# 本人に合わせた作業手順の提示

- 投稿: 壁打ちで具体化した案
- 状態: 検討候補として残す。開発する案の最終決定と、効果の検証は未実施。

## 1. 元の案

Geminiで職員の手本動画を解析して作業工程を整理し、本人に合った写真・短文・音声の手順を作る。本人向けの説明方法や教え方の工夫も新人職員へ引き継ぎ、同じ試行錯誤を繰り返す負担を減らすことを目指す。例として封筒にチラシを入れる作業を想定した。

## 2. Why：誰の、どんな課題か

- カテゴリ候補: 医療・福祉。
- 対象・課題の仮説: 写真などを参照できると作業しやすい本人と、その人に合う教え方を引き継ぐ職員。特に新人が説明方法や工程の区切り方を一から試行錯誤する負担を想定する。
- 根拠: [厚労省の事例集](https://www.mhlw.go.jp/content/11600000/001230884.pdf)に写真・図や工程分割の実践がある。想定する現場で動画から作る必要があるかは未確認。動画が必要な条件、検証方法、棄却条件は「6. 検証・完成度・デモ」に書く。
- 意図: 本人が望む作業を進められる場面を増やす。説明の準備や新人の試行錯誤にかかる時間を減らし、職員が支援に使える時間の余裕につなげたい。
- 時短の扱い: 時短や支援時間の増加は、今後検証する効果の仮説である。検証方法は、準備・撮影・修正を含む作成時間と、新人が未見の作業で教え方を確認する時間を測ること。比較対象は、直接教える方法、写真数枚の手順、汎用AI。棄却条件は、準備・撮影・修正を含めた負担が、直接教える方法や写真数枚と比べて減らない、または増える場合である。そのときは「時短・職員の余裕」をこの案の利点として採用しない。作業完了の速さだけを本人の利益としない。

## 3. What：解決策と最小の体験

- 操作案: 職員が手本と説明を撮影する。Geminiが工程と説明を下書きする。職員が事実と解釈を分けて確認し、本人に合う提示方法や声かけを修正して承認する。承認後の提示内容は固定表示する。新人が、その作業を未見の状態で教え方と手順を確認する。本人への支援で使い、使いにくい部分は職員が改めて承認した内容へ更新する。
- 個人に合わせる内容の候補: 一度に示す工程の数、写真・短文・音声の使い分け、職員が確認した声かけや説明の工夫。診断名だけから自動で決めない。
- MVP候補: 1作業（動画が必要だと考える条件を満たす、工程の多い作業）、動画からの工程整理、本人に合わせた写真と短文の手順、職員の編集と承認、承認後の固定表示、新人が未見の作業で教え方を確認する画面、本人の「手伝って」「やめる」。
- 比較用の作業: 封筒にチラシを入れる作業は、写真数枚で足りうるかの比較に使う。動画解析を中核とするデモの主作業にはしない。
- 対象外: 全利用者への自動最適化、未確認の生成手順の自動公開、承認前の下書きや失敗した生成結果の本人への提示、承認なしの再生成による提示内容の差し替え。

安全のための決まり（設計上の候補。効果や法令適合は未検証）:

- 本人に手順を見せる前に、職員が下書きを確認して承認する。
- 未承認の下書きや、失敗したGeminiの出力は本人に見せない。
- 未確認の生成手順を自動公開しない。
- 承認後の提示内容は固定表示する。承認なしに再生成で差し替えない。
- 本人はいつでも「やめる」できる。「やめる」は便利機能ではなく、作業を止めるための手段とする。「手伝って」は支援を求める手段とする。
- 事実と解釈を分ける。動画・音声に写った動きや職員の声、職員が確認して残した内容は事実側とする。Geminiが分割した工程や生成した説明文は解釈・下書きであり、職員が採否を決める。画面上でも、生成した下書きと職員が確認した内容を、一つの確定手順として混ぜて見せない。
- 手本動画・写真・音声は、本人や職員が写りうる記録として扱う。本人へ何を見せるかは職員が決める。

## 4. How：Google技術と候補比較

- 候補: GeminiをVertex AI経由で使い、動画・画像から工程と説明を整理する。Cloud Runでアプリを動かす。構成の確定と実装は未実施。
- 中核であることの条件（仮説）: 工程の区切り、動きの順番やつまずき・間の取り方、ベテランが手本の最中に出す声かけなど、静止画では残らない情報が手順に必要であること。この条件が成り立たない場合、Geminiの動画解析をGoogle技術の中核とする主張は使わない。棄却条件は「6. 検証・完成度・デモ」に書く。
- メリットの仮説: 動画から工程と説明の下書きを作り、職員が確認した本人向けの調整を新人も参照できる。
- デメリット: 工程の抜け、誤った写真・説明、撮影・修正の負担。
- 比較対象: 直接教える、写真数枚を並べる、汎用AI、[MagnusCards](https://www.magnusmode.com/magnuscards/)。

## 5. AIをどこで、なぜ使うか

Geminiを動画の解析、工程の分割、説明の下書きに使う案。これらは解釈であり、本人への提示方法や新人に引き継ぐ工夫は、職員が事実と照合して確認し、決める。文書整理・調査でのAI利用は[共通記録](intellectual-disability-welfare-review.md#ai利用と判断)を参照。

## 6. 検証・完成度・デモ

動画が必要だと考えている条件（仮説）:

- 工程が多く、どこで区切るかが作業の理解を左右する。
- 動きの順番、つまずきや間の取り方など、静止画では残らない時間情報が説明に要る。
- ベテランが手本の最中に出す声かけが、写真だけでは引き継げない。

写真数枚で足りうるのは、姿勢や配置が数枚の静止画で区別できる作業である。封筒にチラシを入れる作業は、この比較用の作業として残す。

検証方法:

- 比較するもの: 準備・撮影・修正を含む作成時間、新人が未見の作業で教え方を確認する時間、説明や試行錯誤を繰り返す負担。直接説明、写真の手順、汎用AI、既存の手順作成サービスと比較する。
- 動画の必要性: 同じ作業について、写真数枚（必要なら短文つき）で作った手順と、手本動画をGeminiで解析して作った手順を比べる。見るものは、工程の抜けや誤った写真・説明、新人がその作業を未見の状態で教え方を確認できるか、本人が手順を使って必要な支援を求められるか。
- 本人への確認: 手順や説明が使いやすいか、必要な支援を求められるかを確かめる。作業完了の速さだけを本人の利益としない。
- デモ案: 主作業は、上記の「動画が必要な条件」を満たす工程の多い作業にする。資料にない具体的な職場の作業名は、検証するまで新たに定めない。流れは、同じ作業の手本動画、Geminiによる工程の整理（解釈・下書き）、職員が事実と解釈を分けて本人向けに調整し承認、承認内容の固定表示、新人が未見の作業として教え方を確認する、である。封筒にチラシを入れる作業は、写真数枚との比較として見せる。動画から表示までの変化とGoogle技術の役割を説明しやすい。
- 未検証の効果: 新人の試行錯誤の削減、職員の時間の余裕、本人への支援の改善。デモで一連の操作が動いても、これらを実証したことにはならない。

棄却条件:

- 時短: 準備・撮影・修正を含めた負担が、直接教える方法や写真数枚と比べて減らない、または増えるなら、「時短・職員の余裕」という効果仮説はこの案の利点として採用しない。
- 動画の必要性: 想定する作業、またはデモの主作業で、写真数枚（または写真と短文）の手順が、動画から作った手順と同等以上に使えるなら、「Geminiの動画解析がGoogle技術の中核である」という主張は成り立たない。その場合、動画解析を中核にした現在のこの案の立て方は捨てる。提出案としては採用しない。

## 7. 未決定事項・次の確認・学び

### 候補として残す理由

- Geminiの動画解析から本人に合わせた手順を提示する流れが、作業の説明や教え方の引き継ぎに使える可能性がある。ただし中核であることは、第6節の条件を検証するまで仮説である。
- 新人が説明方法を何度も試す負担を減らし、職員の時間の余裕につながる可能性を検討したい。時短は仮説であり、棄却条件は第6節に書いた。
- 動画の入力、工程の整理、本人向けの調整と承認、固定表示、新人の未見ケースでの確認を、一つのデモで説明できる。
- 撮影・確認の負担や既存製品との重複は確認事項として残し、それだけを理由に候補から外さない。

### 残っている確認事項

- 動画が必要な条件と、写真で足りた場合の棄却条件は第6節に書いた。まだ検証していない。
- 撮影と修正の手間を含めても、繰り返しの説明や新人の試行錯誤を減らせるか。減らない場合の扱いは第6節の時短の棄却条件に書いた。
- 既存の手順作成サービスや汎用AIと比べ、何が使いやすくなるか。
- 動画に現れない本人の好みや教え方の工夫を、職員がどう確認・補足するか。

開発による学びは未記入。今後の検討候補として残し、効果は検証して判断する。
