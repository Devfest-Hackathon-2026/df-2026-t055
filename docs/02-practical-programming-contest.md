# 実際のアプリケーション開発に近い競プロ

- 投稿: markun46490:10
- 状態: 仮置き・未検証。以下の具体化は検討用の仮説。

## 1. 元の案

- 競プロや既存のコーディングテストは、実際のアプリケーション開発に直接つながるような問題をとくことはなく、アルゴリズムをひたすらやるのがおもしろくない。ISUCONやCTFのような実務との関わりが近い形式での問題を解くものがほしい。

## 2. Why：誰の、どんな課題か

- カテゴリ候補: 教育
- 対象ユーザー・困る場面（仮説）: アルゴリズムの学習からアプリ開発へ進みたいが、実践的な練習機会を得にくい学習者。
- 解決したい社会課題（仮説）: 開発の実践経験へアクセスする機会の差。単に競プロが面白くないという好みと、学習上の障壁を区別する。
- 根拠: 未確認。学習者へのヒアリングと既存の実践教材の調査で、練習できず困る具体的な作業を確認し、出典・日付を追記する。
- 人間が決める意図: 実務の何を練習させたいかと、達成条件をチームが定義する。

## 3. What：解決策と最小の体験

- 解決の仕組み（仮説）: 小さなアプリの不具合や仕様追加を題材に、変更が要件を満たすかテストで確認できる問題を提供する。
- 操作フロー案: 1問の要件を読む→配布コードを自分の環境で修正する→テストする→結果と解説で振り返る。
- MVP候補: 1問、配布コード、明確な受け入れテスト、解説、振り返りの表示。
- 今回の対象外候補: サーバーで任意コードを実行する採点環境、大会運営、ランキング、大量の問題。
- 既存の手段との差（仮説）: ISUCON・CTF・既存教材と比べ、アプリ開発の特定作業を小さく練習できる価値があるか検証する。

## 5. AIをどこで、なぜ使うか

- プロダクト内の利用案: テスト結果に基づくヒント・振り返りの生成。正誤の基準は人間が定義したテストに置く。
- その場面で使う理由: 学習者ごとに異なるつまずきの説明に役立つかを検証する。
- 人間が判断・確認すること: 学習目標、問題・テストの妥当性、ヒントの正確さ、解答を出しすぎない範囲。
- 開発支援の利用実績: 文書整理は[共通記録](README.md#この文書でのai利用)を参照。以降の利用は場面・理由・人間の判断を追記する。

## 6. 検証・完成度・デモ

- 課題と効果の検証: 学習者に1問を試してもらい、完了状況と修正理由を説明できるかを確認する。結果は未検証。
- UI・UXの確認: 要件、環境の準備、テスト結果、次の操作が分かるかを確認する。
- 安全性・データの扱い: 利用者のコードをサーバーで実行しないMVPを検討する。AIへ送るログ・コードに秘密情報がないか確認し、AI失敗時も固定解説を参照できるようにする。
- 拡張性・保守性: 最初は1問に絞り、問題文・配布コード・テスト・解説を対応付けて管理する。
- デモ構成案: 学習上のつまずき→1問の修正とテスト→振り返り→学習者の確認結果。
