- 状態: 今回不採択（2026年11月5日）。以下は検討時の記録。
- 不採択理由: 修正前後を示すデモは魅力的だが、安全なコード実行と公平な採点基盤の開発負担が大きい。今回は障害者福祉の支援に取り組む11Aを優先した。
- 採択案: [11A 本人に合わせた作業手順の提示](../adopted/11-personalized-task-guidance.md)
- 検討時の状態: 対話と第1回蠱毒の指摘をもとに具体化した構想。課題の根拠、実現方法、効果は未検証。実装済みの事実ではない。

## 1. 元の案

- 競プロや既存のコーディングテストは、実際のアプリケーション開発に直接つながるような問題をとくことはなく、アルゴリズムをひたすらやるのがおもしろくない。ISUCONやCTFのような実務との関わりが近い形式での問題を解くものがほしい。

## 2. Why：誰の、どんな課題か

- カテゴリ候補: 教育。
- アルゴリズムの力はビジネスロジックにも役立つ一方、アプリ開発ではデータベース、N+1などのクエリ、メモリ管理、フロントエンドのフェッチのタイミング、アクセシビリティ、データ保持など、別の知識や判断も求められる。
- 既存のアプリを読み解き、実際の開発に近い課題に取り組みながら、アプリケーション開発を学べる場を目指す。
- 実践機会が不足しているという課題や既存教材との差は仮説。対象者へのヒアリングや既存サービスの調査は未実施。

### 代替との比較（仮説）

- 通常の競プロやコーディングテストは、アルゴリズムや短い関数の正誤が中心で、既存アプリを読んでデータベース、N+1、フロントエンドのフェッチ、アクセシビリティなどを直す経験にはなりにくい、というのが仮説。
- 通常の研修・教材・授業は、アプリ開発の知識を学べる一方、独立した初期状態のチケットを受け取り、既存アプリを直してベンチマークで点数が出る、という反復にはなりにくい、というのが仮説。
- ISUCONやCTFは、元の案が挙げた通り実務との関わりは近い。ただしISUCONは長時間のコンテスト形式が中心で、学習者が短いチケット単位で繰り返す練習にはなりにくい、というのが仮説。CTFはセキュリティ寄りの別領域として扱う。
- この案が狙う差は、1つの既存アプリに対する独立したチケットを受け取り、修正し、人が定めたベンチマーカーでスコアを確認する、短い実務型の反復である。課題の具体例（N+1、フェッチのタイミング、アクセシビリティなど）と、「1つのアプリを修正し、ベンチマークする」デモの流れは、この案の中心として残す。
- 検証方法: 競プロや授業は経験したがアプリ開発の実務課題は少ない学習者に、上記の差が実際に困っていることかをヒアリングする。既存のコーディングテスト、研修教材、ISUCON形式の公開情報が、同じ「既存アプリ＋独立チケット＋ベンチ」をすでに提供していないかも調べる。
- 棄却条件: ヒアリングや調査で、通常の競プロ、通常の研修、ISUCON形式ですでに同じ学習者が同じ練習ができていると分かった場合、この案をハッカソンのプロダクトとしては捨てる。ヒアリング結果や調査結果はまだない。

## 3. What：問題と参加体験

1. 参加者は、実際のアプリに近いコードベースと、達成条件を明記したチケットを受け取る。
2. 理想の入口は、ブラウザ上でファイルの検索・編集やターミナル操作ができる開発環境（ブラウザ IDE）を開くこと。
3. 5日でブラウザ IDE が間に合わない場合のフォールバックは、手元でコードを編集し、差分またはプロジェクトを採点側へ提出すること。ブラウザ IDE が存在する前提の構想だけにはしない。
4. 関連コードや仕様を読み解き、修正してテストを通す。AIの利用は任意。
5. 問題ごとのベンチマーカーを繰り返し実行し、結果を見ながら改善する。最終的な成果はスコアで示す。ピッチのデモは、入口がブラウザ IDE でもローカル編集＋提出でも、「1つのチケットを受け取る → 1つのアプリを修正する → ベンチマークを実行する → スコア（と、後述のレビューが検証を通った場合はそのレビュー）を見る」を見せる。

### 最初の題材と採点指標

- 最初のチケットは N+1 の性能改善とする（設計判断）。対象にする具体的なアプリやコードベースは未決定。
- スコアは、人が事前に定義したベンチマーカーだけが算出する。指標の候補は、固定シナリオにおけるクエリ回数、またはそのシナリオの応答時間、あるいはその両方。数値の閾値・基準値・目標値は未決定であり、ここでは置かない。
- 自動検査では測れない点は推測せず「未計測」と明示する。
- 今後のチケットでは、性能課題なら性能指標、アクセシビリティ課題ならその検査指標など、課題に合ったベンチマーカーを検討する。最初のデモチケットは N+1 に絞る。フロントエンドのフェッチやアクセシビリティ改善は、問題例の候補として残す。
- ECサイトやSNSなど複数のアプリを題材にし、問題を定期的に追加する構想。同じアプリに複数のチケットを用意し、コードベースへの理解を活かせるようにする。各チケットは独立した初期状態から開始し、前の修正を引き継がない。
- 個人の練習にも、企業の採用時のコーディングテストにも使えることを目指す。採用でスコアだけから技術力全体を判断できるとは限らない。

## 4. ハッカソンで示したい範囲

- 一つのアプリを対象に、チケットに取り組み、修正とベンチマークを実行し、結果を確認できるところをピッチの中心にする。入口はブラウザ IDE を理想とし、間に合わなければローカル編集＋提出とする。最初の問題は N+1、採点は人が定義したベンチマーカーによる。
- 既存のコーディングエージェントを使いながら課題に取り組む体験も見せられるとよい。Gemini の位置づけは第6節。5日間で用意できるかは未確認。
- 複数アプリ・定期的な問題追加・企業による出題や成果共有は今後の発展として示す。
- ブラウザ開発環境、実行環境の隔離、安全な採点、コストと実装期間は未検証。設計は第6節に書く。検証できない項目は、デモで実装済みであるかのように見せない。

## 5. AIと企業への共有

- AIの利用は任意。ベンチマークのスコアにAIとのやり取りは含めない。
- 既存のコーディングエージェントと連携し、プロンプトと回答の両方を記録できれば、企業が開発過程を知る参考になる。参加者が企業への共有を選んだ場合、一連の履歴をまとめて共有する構想。記録開始時と共有前に何が記録・共有されるかを示す必要がある。
- MCPや `AGENTS.md` のような指示ファイルに連携方法を記載する案が出たが、具体的な仕組みは未決定。指示ファイルやMCP接続だけで履歴が漏れなく記録される保証はなく、外部ツールでのやり取りも把握できない。
- 将来は企業が問題を作成・公開し、共有に同意した参加者の成果や履歴を見て人材と出会える可能性を検討する。企業向け機能は未実装。

## 6. Google技術・要件

### 中核にする技術

- 指定実行基盤は Cloud Run とする。役割は、提出ごとにテストとベンチマークを使い捨てのコンテナで実行し、終了後に破棄すること。必須の実行基盤（App Engine／Compute Engine／GKE／Cloud Run／Firebase App Hosting／Firebase Hosting）のうち、採点の隔離に使うもの。
- AIの中核は Vertex AI 経由の Gemini とする。役割は、提出の差分とベンチマーク結果からレビュー文を書くこと。Gemini はスコアを付けない、変更しない。AIを使う場合の推奨経路は、[共通メモ](../README.md#要件の扱い)の共有情報に基づく。
- 中核利用、指定実行基盤、費用、安全性は未検証・未実装である。以下は設計判断であり、動いている事実ではない。

### 選定理由（設計判断・仮説）

- Cloud Run は、提出ごとの短い隔離ジョブに合いやすい、というのが仮説。
- GKE は、5日間の構築と運用の負担が大きくなりやすい、というのが仮説。
- Compute Engine は、長めに残る VM になりやすく、提出ごとの隔離と消し忘れ防止が難しい、というのが仮説。
- App Engine は、提出ごとの使い捨てジョブ向きではない、というのが仮説。
- Firebase Hosting と Firebase App Hosting は UI の配信向きで、提出コードの採点を隔離する中核にはしない。Web UI を出す将来または副次の候補にはなり得るが、採点の中核ではない。
- 検証方法: デモ用の提出を Cloud Run の使い捨てジョブで走らせ、起動・隔離・破棄ができるかを確認する。他基盤との実測比較は必須としない。チームの Cloud クレジットは [共通メモ](../README.md) に記載された1チーム20ドルで、これ以外の金額や実測コストは未確認のため書かない。予算アラートの検討は同メモの共通注意に従う。
- 棄却条件: Cloud Run で提出ごとの隔離実行がデモできない場合、指定実行基盤としての Cloud Run 中核は取り下げ、オンラインの隔離採点を実装済みであるかのように見せない。その場合の見せ方は次項のフォールバックに従う。

### 隔離と採点の安全性（未検証の設計）

- 設計: 提出ごとに Cloud Run のジョブまたはコンテナを1つ作り、その実行環境を他の参加者の提出と再利用しない。参加者から見える環境に秘密情報を置かない。
- 1日目の検証: ワークスペース外を読もうとする、または実行が残り続けようとするサンプル提出を走らせ、隔離されていることとジョブが破棄されることを確認する。この検証は未実施。
- フォールバック: 隔離を示せない場合、オンラインの隔離採点はできたことにしない。ピッチではローカル実行のベンチマーク、または運営側が用意した環境での採点結果を見せ、その旨を説明する。
- セキュリティ監査や侵入試験の結果はない。

### Gemini レビューの検証可能な設計（仮説）

- 分担: 人が定義したベンチマーカーが点数を出し、Gemini は説明だけを書く。
- 入力: 提出差分、ベンチマークの計測値、チケットの達成条件。
- 出力: レビュー。各指摘は、コード上の位置と計測された値の両方に結びつける。測っていないことは「未計測」と書く。
- やってはいけないこと: スコアの算出や変更。参加者が自分で見つけるべき模範解答をそのまま漏らすこと。
- 検証方法: デモ用の N+1 チケットで、(a) 模範解答を漏らしていないか、(b) 計測値と矛盾していないか、誤った箇所を引用していないか、(c) LLM を使わない固定の解説文テンプレートより役立つか、を確認する。
- 棄却条件: 解答の漏洩が多い、計測と矛盾することが多い、または固定の解説と差がない場合、Gemini をプロダクトの中核機能からは外す。Cloud Run による隔離採点は残す。レビューが動いている事実はない。
- 参加者が使う AI の種類は任意であり、Gemini に限定する意図はない。実行基盤や他社AIの扱いを含むハッカソン要件は、[共通メモ](../README.md#要件の扱い)に記載された共有情報を原本と照合する必要がある。
