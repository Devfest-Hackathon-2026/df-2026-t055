## 1. 元の案

- 世の中の高齢者は、お墓参りに行く体力的な余裕がなく、バーチャル修学旅行のようにお墓参りを遠隔で行える方法があるとよいのではないか。

## 2. Why：誰の、どんな課題か

- カテゴリ: 医療・福祉
- 対象ユーザー・困る場面（仮説）: 移動や体力の制約で、希望していてもお墓参りに行けない高齢者。
- 対話で出た一例（仮説。本人の気持ちの確認は未了）: 杖を使い、階段を上るのも難しい高齢者がいる。お墓へ行くには、仕事のある家族に車を出してもらう必要がある。家族に頼みにくいかどうかは確認しておらず、ここでは推測しない。この一例を、検証で確かめる場面のたたき台にする。
- 解決したい社会課題（仮説）: 身体的な制約によって、本人が大切にしている行為への参加機会が限られること。遠隔参加が現地訪問と同じ満足につながるとは断定しない。
- 根拠の扱い: 調査データやヒアリング結果はまだない。身近な一例と投稿者の問題意識に基づく仮説である。出典のある統計や、本人の発言としては扱わない。
- 人間が決める意図: 本人にとって意味のある参加方法を本人・家族と決める。
- 検証方法: 対象者本人と、車を出したり撮影したりしうる家族に、次を聞く。(1) 現地に行きたいが、移動や体力、家族の送迎の都合で行けないことがあるか。(2) 自宅のスマートフォンで墓所の映像を見ながら手を合わせることを、本人が望むか。(3) 家族の写真・動画共有やビデオ通話で足りているか、何が足りないか。聞いた内容には、対象と日付を出典として追記する。
- 棄却条件: 本人が遠隔でのお参りを望まない、または映像を見ても参加した気持ちにならないと答えた場合。既存の写真・動画共有や通話で本人が足りると答えた場合。行くこと自体の障壁が、対話の一例以外に見つからず、仮説が個人の推測のままになった場合。

## 3. What：解決策と最小の体験

- 解決の仕組み（仮説）: 許可を得て撮影した墓所の映像と短い案内を、招待された本人だけが、離れた場所から自分のペースで見られるようにする。
- 撮影の担い手（仮説。第1回討論で明確化）: 家族が自分のお参りのついでに撮影する。新しい現地訪問を家族に増やすのではなく、家族がもともと行く機会の映像を残し、本人はその映像をあとから何度でも見られるようにする。代替として、墓所の管理者が提供する映像を、許可が取れた場合に使う。
- 操作フロー（MVPで採用）: 招待を開く → 大きなボタンで墓所の映像を再生し、見ながら手を合わせる → 大きなボタンでお参りを終える。操作は再生と終了の2つに絞る。
- MVP: 1か所の映像、招待による限定共有、大きな操作ボタンと固定の短い案内（文字または音声）。
- 今回の対象外: 現地撮影の代行網、全国の墓所対応、ライブ通話の自前実装、花や線香を供える操作（没入感の案は出たが、必要性未確認のため採用しない）。
- 既存の手段との差（仮説）: 通常の動画共有やビデオ通話と比べ、対象者が操作しやすく、お参りに集中でき、映像の公開範囲を招待先に限定できるか。
- UI の検証方法: 対象者に案内だけを渡し、招待を開く・再生する・終了する、が一人でできるかを見る。文字と音声のどちらが分かるかも確認する。結果は未確認。
- 棄却条件: 大きなボタンと案内を1回改善しても、対象者が再生と終了を一人でできない場合（専用アプリの操作上の差が立てられない）。家族の訪問時撮影も管理者提供もできず、許可の取れた映像を1本も用意できない場合。

## 4. How：Google技術と選定

中核は、非公開の墓所映像を扱う Cloud Storage と、招待・閲覧許可を処理する指定実行基盤の Cloud Run とする。静的ページのホスティングだけでは、招待先に限った非公開の閲覧を扱えきれない、という比較で決めた。費用・通信量・保管期間の数値は未確認で、実装時に確認する。

| 比較対象 | 役割 | 判断 |
| --- | --- | --- |
| Cloud Storage | 墓所の映像の保管・配信。アプリ本体と映像を分け、公開URLにしない | 採用。中核のデータ置き場 |
| Cloud Run | 招待の確認と、許可した人だけが映像を見られるようにする指定実行基盤 | 採用。中核の実行基盤 |
| Firebase Hosting（静的ページ） | 閲覧画面だけを置く比較対象 | 不採用（実行基盤としては使わない）。静的ページは映像の再生画面には使えるが、招待と非公開映像の制御は別に必要になる。制御まで静的ファイルだけに置くと、共有リンクの扱いを誤りやすい |
| 既存の動画共有・通話 | 専用アプリを作らずに済ませる比較対象 | プロダクトとしては採用しない。検証の結果、これで本人が足りると言えば案自体を捨てる（第9章の棄却条件） |

- 採用技術と選定理由: 墓所の映像は墓石の家名や人物が映りうるため、公開の静的ページや誰でも開ける動画リンクには置かない。Cloud Storage に非公開で置き、Cloud Run が招待を確かめてから閲覧を許可する。これが通常の静的ページや動画共有との差であり、Google技術を中核にする理由である。
- 採用しなかった案と理由: 実行基盤としての Firebase Hosting は、小さな画面には向くが、招待と非公開配信の制御を持てない。既存の動画共有・通話は、操作や公開範囲の点で対象者に足りるか未確認なので、足りると分かった時点でこの案を捨てる。
- Gemini は中核にしない。理由と採用・不採用の条件は次章。

## 5. AIをどこで、なぜ使うか（使わない判断を含む）

## 6. 撮影許可とデータの扱い（設計）

意識だけでなく、デモで守る手順として書く。許可が取れていない映像は使わない。

- 許可を取る相手: (1) 見る本人（遠隔で見ることへの同意）(2) 撮影する家族 (3) 墓地・霊園の管理者（敷地や墓石を撮ってよいか）(4) 映像に人物が映る場合は、その人。
- 撮るもの: 墓所の映像。墓石の家名などは個人に関わる情報になりうるので、公開範囲と保管先を本人・家族と決める。
- 公開範囲: 招待された本人と、映像を用意した家族に限る。誰でも開ける公開リンクにはしない。
- 仕組み（仮説。実装は未了）: Cloud Storage のオブジェクトは非公開。Cloud Run が招待を確認し、許可できたときだけ閲覧できるようにする。保管期間は家族と決めた日までとし、過ぎたら配信を止める（日数の実測値はまだない）。
- 失敗時: 招待が無効、許可がない、映像が用意できない、通信できない、のいずれでも、「いま映像を見られません」とだけ案内し、映らないはずの映像を出さない。
- 撮影の頻度（仮説）: 家族の通常のお参りのついでに撮り、同じ映像を本人が繰り返し見る。新しい映像が要る頻度は本人と家族の希望で決める。未確認。
- 棄却条件: 本人・撮影する家族・管理者のいずれかから必要な許可が取れず、デモ用の映像を正当に用意できない場合。

## 9. 棄却条件（まとめ）

次のいずれかが検証で分かった場合、この案は捨てる。

1. 本人が遠隔でのお参りを望まない、または映像では参加した気持ちにならない。
2. 既存の写真・動画共有やビデオ通話で、本人が足りると答える。
3. 招待による非公開制御が不要で、静的ページや公開動画だけで足りる（その場合、Cloud Run を中核にする理由がなくなる）。
4. 家族の訪問時撮影も管理者提供もできず、許可の取れた映像を用意できない。
5. 本人・撮影する家族・管理者など、必要な許可が取れない。
6. 大きなボタンと案内を1回改善しても、対象者が再生と終了を一人でできない。

## 11. 対話で出たこと

- 身近な例として、杖を使い、階段を上るのも難しい高齢者がいる。お墓へ行くには、仕事のある家族に車を出してもらう必要がある。家族に頼みにくいかどうかは本人の気持ちを確認しておらず、推測にすぎない。
