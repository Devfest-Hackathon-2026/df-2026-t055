# 設計変更案：すべてのテキスト入力欄で音声入力を使えるようにする（a11y）

提案日：2026年11月7日。状態：レビュー中。

対象は[設計フリーズ v0.1](design-freeze-2026-11-07.md)に基づくアプリ全体。文字を入力・編集できるすべての欄で、キーボード入力に加えて音声入力を利用できることを、アクセシビリティの共通要件とする。

## 目的と適用範囲

文字を打つことが難しい人や、話して入力する方法を選びたい人が、自分に合う方法で入力できるようにする。利用者は同じ入力欄で、文字入力と音声入力を切り替え、組み合わせて使える。

職員・本人・新人の全画面を対象とし、通常のフォーム、モーダル、検索欄、ログイン画面など、文字入力欄を設けるすべての箇所に適用する。今後追加する入力欄にも同じ要件を適用する。

| 画面・用途 | 対象となる入力の例 |
| --- | --- |
| 作業の登録 | 作業名 |
| 手順の下書き編集・承認前の確認 | 工程の説明、本人向けの注意、観察内容、声かけ、教え方、完成基準、確認事項への対応記録 |
| 本人プロフィール | 希望や説明方法の好みなど、文字を入力・編集する項目 |
| 追加機能のフォーム・モーダル | AIへの修正依頼、支援中のつまずきや支援内容など、各案の採用時に設ける入力欄 |
| その他の画面 | 検索やログインなど、文字を入力できる欄すべて |

音声入力でも、入力先の権限、文字数、形式、必須項目の検査は文字入力と共通にする。承認済み手順のように編集を許可していない内容は、既存の権限と更新手順を保つ。

## 共通の入力操作

1. 入力欄ごとに対象が分かる「音声で入力」ボタンを設ける。例えば、作業名の欄には「作業名を音声で入力」と表示する。
2. 利用者が開始を選んだときにマイクの利用許可を求め、録音を始める。録音中であることと、停止・キャンセルの操作を表示する。
3. 録音を止めると文字起こしを表示する。利用者は内容を確認・訂正し、対象の入力欄へ反映する。既に入力した文章への追加・置換は、反映する前に確認できるようにする。
4. 反映後も文字入力・音声入力で編集を続けられる。音声認識の完了だけではフォームを送信せず、保存・修正依頼・承認は既存の操作で行う。

## 操作のアクセシビリティと失敗時の動作

- 音声入力の開始・停止・キャンセル・反映をキーボードでも操作でき、フォーカス位置が分かるようにする。モーダルを閉じた後は、開いた操作元へフォーカスを戻す。
- 入力欄とボタンにはラベルを付け、支援技術が読み取る名前にも画面に見える文言を含める。録音中・認識中・完了・失敗は、画面の文字とスクリーンリーダーへの通知で伝える。
- マイクの許可拒否、非対応の環境、通信断、認識失敗、キャンセルでも入力済みの文章を保持し、文字入力を続けられるようにする。再試行時も、確認前の認識結果で既存の文章を上書きしない。
- 音声認識の方式、対応する端末・ブラウザ、音声と文字起こしの送信先・保存方針・費用を実装前に決める。ログイン情報などの機微情報を扱う欄も確認対象とし、認証情報を外部の音声認識サービスやログへ送らない方式を選ぶ。

入力方法を切り替えて使える方針は[W3Cの入力方式に関する解説](https://www.w3.org/WAI/WCAG22/Understanding/concurrent-input-mechanisms.html)、表示ラベルと支援技術が読み取る名前の対応は[W3CのLabel in Nameの解説](https://www.w3.org/WAI/WCAG22/Understanding/label-in-name.html)を参考にする。

## 確認すること

- 全画面の入力欄を一覧にし、通常のフォーム・モーダル・権限別の画面を含め、すべてのテキスト入力欄で音声入力を使えることを確認する。上の表にない欄も対象にする。
- 文字と音声の切替、既存文への追加・置換、誤認識の訂正、保存前のキャンセルを確認する。
- キーボード操作、フォーカスの移動、スクリーンリーダーによるラベルと状態の読み取りを確認する。
- マイクの許可拒否、通信断、認識失敗、非対応環境でも入力内容が失われず、文字入力で作業を続けられることを確認する。
- 音声入力にも既存の入力検査と権限が適用され、音声認識だけで送信・承認が実行されないことを確認する。
- 対応する端末・ブラウザで、認識精度、訂正の負担、入力にかかる時間と使いやすさを確認する。
