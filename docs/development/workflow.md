# 仕様変更・レビュー・履歴の扱い

1. **仕様を変えるPRは該当する機能仕様と関連する共通契約を更新**する。目的・対象ユーザー、入力／出力、状態遷移、安全条件、受け入れ条件の変更を明示する。
2. 未採用の提案PR、採択前の調査、旧設計資料、過去のAI実装指示は **意思決定の履歴**。現行仕様と並列の仕様としてAIに扱わせたり、矛盾した部分を勝手に統合したりしない。調査の根拠を使う場合は[設計根拠の参照規則](../research/sources.md)の参照ルールに従う。
3. API・スキーマ変更はフロント・API・AI担当で合意し、共有型・テスト・対応する機能仕様と共通契約を同じPRで更新する。承認境界、「やめる」など安全条件の緩和は暗黙に行わない。
4. 実装済みの挙動と仕様が食い違う場合、コードが正しいと決めつけず、差分を報告しチームで判断する。実装・検証済みかどうかはテスト結果に基づいて記録する。
5. 以下の旧ファイルを残すのは履歴と根拠のため。現行の実装指示に引用する場合も、まずdocs内の現行仕様で整合を確認する。

旧資料は [アーカイブ](../archive/README.md) にまとめている。

- [2026-11-07 設計フリーズ v0.1](../archive/design-freeze-2026-11-07.md) は統合元の技術詳細を記録している。
- [採択案11A](../archive/adopted/11-personalized-task-guidance.md) は採択理由と検討経緯を記録している。
- [構成図](../archive/architecture-2026-11-07.png) は2026-11-07時点の構成を示す。

**AIエージェントへの指示：** 実装前に文書索引から担当機能・共通契約・受入条件を読んで実装範囲・安全条件・未確定項目を抽出する。旧文書や他PRから新機能を無断で採用しない。曖昧な点や仕様衝突はPRへ記録し、推測で制度や本人の能力に基づくUI分岐を追加しない。
