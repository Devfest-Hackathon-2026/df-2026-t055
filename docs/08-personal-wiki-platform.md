# 自分専用wiki作成プラットフォーム

- 投稿: 不明（元の投稿に記載なし）
- 状態: 仮置き・未検証。以下の具体化は検討用の仮説。
- 記入方針: 元の案と追加の仮説を分ける。出典・効果・実績を推測で確定しない。

## 1. 元の案

- エンジニア業界では自分の知識をqiitaやzennなどでアウトプットすることが多いが、他業界ではどうか。
- エンジニアのアウトプット文化を他の業界にも浸透させて、業界の活発、交流を促したい。

## 2. Why：誰の、どんな課題か

- カテゴリ候補: 教育（仮）。知識の整理・共有が学習の機会にどうつながるかを具体化する必要がある。
- 対象業界の候補（仮説、1つに絞る。未決定）: 現場の手技・判断が属人化しやすく、文章での発信文化が相対的に薄い業界を候補にする。
  - 介護・福祉: ケアの工夫や移乗のコツなどが個人に溜まり、事業所を越えて共有されにくい。
  - 飲食: レシピの工夫、接客・クレーム対応の知見が口頭伝承に寄りやすい。
  - 建設・製造の現場職: 安全や段取りの暗黙知がベテランに集中し、若手が学ぶ機会が限られる。
- 対象ユーザー・困る場面（仮説）: 経験や知識は持っているが、①文章にまとめる時間と構成力が壁になり書けない ②社外秘・個人情報に触れそうで公開の判断が怖い ③書いても読まれず続かない、という三重の障壁で発信に至らない人。
- 解決したい社会課題（仮説）: 個人の経験・知識が本人の頭の中と現場に閉じ、他者が学んだり交流したりする機会が限られること。他業界に発信文化が「ない」とは断定せず、エンジニア業界との差（アウトプットを後押しする道具と場の有無）を調べる。
- 根拠: 未確認。対象候補業界の既存の発信・学習手段（業界誌、SNS、社内共有の実態）を調べ、当事者に「知識を共有したくてもできなかった場面」を聞いて出典・日付を追記する。
- 人間が決める意図: 最初の対象業界を1つに絞り、その業界の「型」（手順・事例・失敗談など共有されやすい知識の形）を当事者と一緒に決める。

## 3. What：解決策と最小の体験

- 解決の仕組み（仮説）: 「自分用wiki」を土台にし、書く負担と公開の不安を分けて下げる。
  1. メモから始める: 箇条書き・音声メモ・写真メモなど雑な入力を受け付け、AIが業界の型に沿って見出し・手順・注意点に構造化したページ案を作る。本人はゼロから書かず、直すところから始められる。
  2. 非公開が初期状態: ページはまず自分用wikiに非公開で溜まる。公開は本人がページごとに明示的に選ぶ操作でのみ行い、AIが自動で公開することはない。
  3. 公開範囲の選択: 「自分のみ／リンクを知っている人／全体公開」をページ単位で選べる。公開前に、個人情報・機密に触れそうな箇所をAIが候補として指摘し、本人が確認する。
- 操作フロー案: メモを入力する → AIのページ案を確認・編集する → 非公開で保存する → 公開チェックを確認し、必要なページだけ公開範囲を選んで公開する。
- MVP候補:
  - 対象1業界に絞ったページの型（テンプレート）1〜2種類
  - メモ（テキスト）からページ案を生成する機能
  - 編集、非公開保存、ページ単位の公開操作と公開ページの閲覧
- 今回の対象外候補: 全業界対応、フォロー・コメント等の交流機能一式、自動公開、音声・画像入力（MVP後に検討）、社内システムや機密資料の取り込み。
- 既存の手段との差（仮説）:
  - 汎用ノート／wiki（Notion等）との差: 自由度が高い反面「何をどう書くか」の型がなく、書く負担が下がらない。本案は業界の型＋下書き生成で書き始めを支援する。
  - ブログ／SNSとの差: いきなり全体公開が前提で、公開の心理的・安全的な壁が高い。本案は非公開の自分用wikiから段階的に公開できる。
  - Qiita／Zennとの差: エンジニア向けの文化と読者層が前提。他業界向けの型と読者を想定する点が異なる（他業界に同種の場がないかは調査して確認する）。

## 5. AIをどこで、なぜ使うか

- プロダクト内の利用案: ①メモの構造化とページ案の下書き ②公開前チェックでの「個人情報・機密に触れそうな箇所」の候補提示。
- その場面で使う理由: 対象者の壁は「知識がない」ことではなく「文章化と公開判断」にある（仮説）。文章の構成はAIが支援しやすい一方、内容の正しさと公開可否は本人の判断が必須であり、役割分担が明確にできる。
- 人間が判断・確認すること: 元のメモとの一致（AIが足した内容は採用しない）、事実と出典、公開範囲の最終決定。AIは公開操作を絶対に行わない。
- 開発支援の利用実績: 文書整理の共通記録は[README](README.md#この文書でのai利用)を参照。以降は場面・使い方・理由・人間の判断を追記。

## 6. 検証・完成度・デモ

- 課題と効果の検証: 対象業界の人2〜3人に、同じ知識メモから①普段の手段（メモ帳やWord等）と②本案のAI下書き経由でページを作ってもらい、所要時間・修正量・「これなら公開してもよい」と思えたかを比較する。結果は未検証。
- UI・UXの確認: 入力→編集→保存→公開範囲の選択を一人で完了でき、現在の公開状態が常に画面で分かるかを確認する。
- 安全性・データの扱い: 非公開を初期状態とし、下書きが所有者以外に見えない構成にする。入力時に機密・個人情報を入れない注意喚起を表示し、生成失敗時も元のメモを失わない。公開ページの取り下げ（非公開に戻す）操作を用意する。
- 拡張性・保守性: 最初の業界とページ作成に絞り、「本文」「公開状態」「生成処理」を分離する。業界の型はテンプレートとして差し替え可能にし、他業界への展開時に中核を変えずに済む構成を検討する。
- デモ構成案: 知識はあるが発信できていない場面（例：ベテランの工夫が口頭でしか伝わらない）→ 雑なメモを入れる → AIが型に沿ったページ案を出す → 本人が直して非公開保存 → 公開前チェックを確認して1ページだけ公開する、までを見せる。
