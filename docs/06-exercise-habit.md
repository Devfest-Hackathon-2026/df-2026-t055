# 運動の習慣化アプリ

## 1. 元の案

- 生活習慣病や医療逼迫などの多方面の課題へのアプローチ
- 日々の生活習慣の見直しを行わせ、健康寿命を伸ばす。
- それぞれの年代にあった運動アプローチを行い長い人生を最後まで楽しくする。
- UIUXの工夫を行い、誰でもモチベーション高く続けられる工夫を行うべき

## 2. Why：誰の、どんな課題か

- カテゴリ候補: 医療・福祉
- 対象ユーザーの捉え方（レビューで重視が決まった軸）: 対象を特定の年代で切るのではなく、**若い世代（自分たちと同世代）から年を重ねていくまでの「同じ人の人生の変化」に伴走する**ことを中核に置く。
  - 年代とともに変わるもの（仮説）: 体力・筋力のピークと低下、代謝の変化、使える時間（学業・仕事・子育て・介護）、運動への不安やハードル。
  - アプリの役割: その時々の体力と生活に合った運動アプローチに推薦を変えていき、「長い人生を最後まで楽しくする」ための習慣を切らさないこと。
  - MVPの初期対象は開発期間の制約上どこかの層に絞る必要があるが、推薦の仕組み自体は年代変化に追随できる設計にする（初期対象の層は未決定。まず同世代から始めるのが候補）。
- 継続を阻む理由と、本人の実感（仮説＋チームメンバーの経験）:
  - 目標が高すぎる: 他人の動画や話を見て「明日から10キロ走ろう」と、自分の現在地とかけ離れた目標を立ててしまう（Koki本人の経験として記録、2026-11-05）。一度崩れると全体をやめやすい。
  - 記録そのものが面倒: テキスト入力が前提だと、記録の手間自体が継続の壁になる。
  - できなかった日の罪悪感: 連続記録が途切れることへの落胆が離脱を招く。
  - 生活は規則正しくいかない: 残業だけでなく、出張・旅行・イベントなどで環境も時間も日ごとに変わり、「いつもの運動」ができない日が必ず出る。
- 解決したい社会課題（仮説）: 運動習慣を続けにくいこと。生活習慣病や医療逼迫、健康寿命への影響は背景として扱い、短期間の開発で実証した効果としては扱わない。
- 根拠: 一部のみ確認。チームメンバー本人の「目標を高く持ちすぎて続かない」経験（2026-11-05、本人談）を記録済み。年代別の体力・生活変化と運動習慣に関する公的統計（スポーツ庁の調査など）は未確認で、出典を確認して追記する。
- 人間が決める意図: ライフコースのどの変化に推薦を追随させるか（体力指標・生活イベントなど）と、健康効果の訴求範囲の線引きをチームで決める。

## 3. What：解決策と最小の体験

- 解決の仕組み（仮説）: 「現在地に合った推薦」と「崩れた日のリカバリー」を両輪にする。
  1. 現在地ベースの目標提示: 初回と定期の簡易分析（体力の自己申告、生活パターン、実施履歴）から、「これくらいやればOK」という現実的なラインを提示する。他人基準の高すぎる目標を、本人の現在地に引き戻すことが目的。
  2. 年代・体力に応じた推薦の変化: 年齢と体力の変化に合わせて、種目・強度・量の推薦を変える（例：若年層は習慣の土台づくりと強度の幅、中年層は運動不足の解消と時間効率、高年層は筋力・バランス維持と安全優先。詳細は対象データの整備と合わせて決める）。
  3. 記録方法の多様化: テキスト入力に固定せず、音声入力・選択式（実施／見送りと理由をタップ）など、その場で一番楽な方法で記録できるようにする。
  4. 罪悪感を薄める継続設計: Duolingo のストリーク（連続記録）を参考にしつつ、途切れても修復できる仕掛け（フリーズ的な猶予）や、「連続」より「再開したこと」を評価する見せ方で、できなかった日の落胆を小さくする（具体的な仕様は検証して決める）。
  5. その日の代替案: 天気・出張・旅行・イベントなど、その日の状況（いる場所、使える空間、空き時間）に応じて、室内やその場でできる運動を代替案として推薦する。「いつもの運動ができない＝休み」ではなく、「今日できる形」に変換する。
- 操作フロー案: 初回設定（年代・体力・生活パターン）→ 現在地に合った今日の提案を確認 → 実施／見送りを楽な方法（音声・タップ等）で記録 → 状況が変わった日は代替案に切り替える → 定期的に振り返り、目標ラインと推薦を更新する。
- MVP候補:
  - 初期対象を1層に絞ったオンボーディングと現在地分析
  - 2段階の現実的な目標ライン提示（最低ライン＋できたら上乗せ）
  - 音声・選択式を含む記録入力
  - 見送りと理由の記録、状況に応じた代替案の提示
  - ストリークの修復など、再開を促す継続表示
- 今回の対象外候補: 全年代の同時対応（仕組みは年代適応可能に設計するが、初期データと検証は1層に絞る）、診断・治療の提案、ウェアラブル・ヘルスケア連携、健康寿命の改善効果の断定、競技・記録向上向け機能。
- 既存の手段との差（仮説）: 一般的な運動記録アプリは「実施した運動の記録・分析」、継続支援アプリは通知やストリークによる動機づけが中心。本案は「本人の現在地と年代変化に合わせた推薦」と「崩れた日の代替案・再開支援」に絞る点が差になるかを検証する。

## 4. How：Google技術と候補比較

技術は未決定。実行基盤は[指定の6種類](README.md#要件の扱い)から1つ以上選ぶ。

推薦方式の基本方針（レビュー反映）: いきなり生成AIに推薦を作らせず、**運動種目・回数・セット数などのキュレーション済みデータセットを用意し、ディシジョンモデル（ルール／決定木ベース）で条件に合わせて動的に組み立てる**方式を第一候補にする。コストと応答速度を抑え、安全性（出す種目の範囲）を人がコントロールできるため。

| 候補 | 役割・採用理由の仮説 | メリット | デメリット・要確認 |
| --- | --- | --- | --- |
| ディシジョンモデル＋運動データセット（Cloud Run 上に実装する候補） | 現在地・年代・その日の状況から種目と量を組み立てる推薦の中核 | 応答が速くコストが低い。出される種目・強度をデータ側で制御でき、安全性を担保しやすい | データセットの整備（種目・強度・年代別の適否）を人が行う負担。組み合わせの表現力に限界がある |
| Gemini（Vertex AI経由を候補） | 振り返りの言語化など、推薦の補助に限定する候補 | 記録の要約や問いかけなど言語化が要る場面には向く | 推薦の中核にするとコスト・応答速度・安全性の制御が難しくなる。要件上「Google技術／Geminiの中核利用」が必須のため、補助に留める場合に要件をどう満たすか運営要件との照合が必要 |
| Cloud Run | 推薦・記録APIの指定実行基盤候補 | ディシジョンモデルとデータ参照をサーバー側に寄せられる | アクセス制御・費用の設計 |
| Firebase Hosting＋Firestore（候補） | 記録画面の配信とデータ保存の比較候補 | 日々の入力画面を軽く構成できる | 推薦処理との役割分担が必要 |

- 採用技術と選定理由: 未決定。ディシジョンモデル方式を第一候補とし、生成AI方式と「推薦の納得感・応答速度・コスト・運用負担」で比較したうえで決める。Google技術の中核利用という要件との整合も確認する。
- 採用しなかった案と理由: 未決定。通知中心（リマインド強化）／記録中心（手帳型）の体験、および生成AIに推薦を丸ごと作らせる方式を、理由とともに記録する。

## 5. AI・モデルをどこで、なぜ使うか

- プロダクト内の利用案: 推薦は原則としてディシジョンモデル＋データセットで行う。生成AI（Gemini）を使う場合は、週次振り返りの要約や問いかけなど「言語化」の場面に限定する候補とする。
- その場面で使う理由: 推薦に必要な判断（現在地・年代・状況→種目と量）は、整理されたデータと決定ルールで再現性高く処理でき、その方が速く安く安全。逆に記録の振り返りを本人の言葉に寄せて言語化する処理は、生成AIが向く。この切り分け自体を検証材料にする。
- 人間が判断・確認すること: データセットに載せる種目・強度・年代別の適否（安全ライン）、目標ラインの決め方、生成AIに渡す記録の範囲。AI・モデルに診断や無理な運動の指示をさせない。体調不良の記録がある日は運動を促さない。
- 開発支援の利用実績: 文書整理の共通記録は[README](README.md#この文書でのai利用)を参照。以降の利用は場面・理由・人間の判断を追記する。

## 6. 検証・完成度・デモ

- 課題と効果の検証: 対象層の3〜5人に5日間使ってもらい、①提示された目標ラインが「これならできる」と感じられたか ②記録方法ごとの入力時間と使われた割合 ③代替案が提示された日に実施できたか ④ストリーク修復の仕掛けが再開に効いた場面、を確認する。結果は未検証で、長期の健康効果は別途検証が必要と明記する。
- UI・UXの確認: 対象者が設定→記録→振り返りを一人で完了できるか、音声・選択式の記録が実際に楽か、「見送る」が罪悪感なく選べる文言・配置かを確認する。
- 安全性・データの扱い: 体調・健康情報は必要最小限にし、公開機能を持たない。推薦データセットの安全ラインを人が管理する。推薦処理が失敗しても記録データは失われない設計にする。
- 拡張性・保守性: 「記録」と「推薦（モデル＋データ）」を分離し、年代別のデータ追加やモデルの差し替えで推薦を更新できる構成にする。これがライフコース適応の実装上の土台になる。
- デモ構成案: 他人の動画を見て「明日から10キロ」と高い目標を立てる場面 → 現在地分析で現実的なラインが提示される → 出張の日は室内でできる代替案に切り替わる → できなかった日があっても修復の仕掛けで再開する → 年代が進んだとき推薦がどう変わるかのイメージ（将来像として明示）→ 短期検証の結果と限界。
