# 設計変更候補：職員が音声でもAIへ修正を依頼する

提案日：2026年11月7日。状態：追加候補。

対象は[設計フリーズ v0.1](design-freeze-2026-11-07.md)の職員向け下書き編集画面。第9節の「あれば枠」として採否を検討する。

支援中に得た指摘を蓄積し、後から修正に使う流れは、[支援記録による手順の改善候補](support-feedback-improvement-proposal.md)にまとめる。

## 目的と既存設計との差分

AIが作った作業手順の下書きに対して、職員が修正を繰り返す場面を想定する。修正内容を話して伝えられるようにし、入力の負担を減らすことを目指す。

既存設計の第2節には、職員が工程の区切り、説明、写真位置を直接編集する操作がある。追加する候補は、テキストまたは音声でAIへ修正を依頼し、修正案を受け取る操作である。

## 操作の例

1. 職員が原動画と下書きを確認し、修正したい工程を選ぶ。
2. 修正依頼をテキストで入力するか、録音ボタンで話す。例：「5番を、紙を押さえる工程と巻く工程に分けて。説明も短くして」。
3. 音声入力の場合は文字起こしを表示し、職員が内容を確認・訂正してから「修正を依頼する」を押す。
4. AIが修正案を返す。職員は変更前後と原動画を照合し、採用する変更を下書きへ反映する。必要なら再度修正を依頼する。直接編集も利用できる。
5. 職員が写真・説明・本人への提示内容を確認し、既存の承認操作へ進む。

## 既存の確認・承認との接続

- 修正案は職員向けの下書きとして表示する。AI原文と職員が採用した内容を分けて保持する。
- 修正案の採用で内容が変わった工程は照合・確認をやり直し、全体の「本人への提示内容確認済み」も再確認する。
- 承認済みの内容を変える場合は、新しい下書きから新版を作る。実行中の本人セッションは開始時の版を使い続ける。
- マイクを利用できない場合や音声認識に失敗した場合は、テキスト入力または直接編集で修正を続けられる。

## 採用前に確かめること

初回生成後に必要となる修正の内容・回数と、文字起こしの訂正を含めた入力負担を確認する。音声入力、テキスト入力、直接編集を比較し、音声入力を追加する効果を判断する。

採用時には、フロント担当とAI担当が修正依頼のAPI・出力検査、音声認識方式、音声データの送信先・保存方針・費用を具体化する。中核機能の完成を遅らせる場合は、今回の実装対象から外す。
