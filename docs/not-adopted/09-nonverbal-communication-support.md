# 声・身振りから意思確認を支える

- 投稿: 会話内で提起された案（特定の個人の事例ではない）
- 状態: 今回不採択（2026年11月5日）。以下は検討時の記録。
- 不採択理由: 職員の推測を本人の意思の正解として固定するリスクがある。本人の意思をAIが推定する方向には進めず、職員が確認した手順を共有する11Aを選んだ。
- 採択案: [11A 本人に合わせた作業手順の提示](../adopted/11-personalized-task-guidance.md)
- 検討時の状態: 保留・未検証
- 弱点改善の改訂: 2026-11-05、第1回蠱毒で指摘された弱点（Gemini が候補のままで未採用、検索フロー案のみ、場面が未特定、入力負担が未確認、ベテランの推測が固定されるリスク、精度・利益を示せないと明記済み、デモが架空検索のみ）を受け、Gemini が必要だと仮定する具体場面を食事に1つ決めた。ルール参照で足りる場合の棄却条件を書き、事実／解釈／確認方法／本人の反応を分ける記録欄は強みとして残した。以下の具体化は検討用の仮説であり、採用済みの仕様や確認済みの事実ではない。

## 1. 元の案

発語による意思表出が難しい人の声や振る舞いについて、長く関わった職員が経験から理解していることを、新人にも引き継げないか。食事・排せつ・不快さなどで表現が違う可能性を想定した。

## 2. Why：誰の、どんな課題か

- カテゴリ候補: 医療・福祉。
- 対象・課題の仮説: 本人の表現に慣れていない職員が、何をどう確認すべきか分からない。
- 今回決めた具体場面（仮説）: 食事中に、声や身振りから「食べたくない」「休みたい」「別のものを望む」「不快そう」などと取れる反応が出たとき、新人職員が何を観察し、どう本人へ確かめるか分からない。
- この場面を選んだ理由: 元の案が食事・排せつ・不快さを挙げていたこと、および第1回討論で「場面が未特定のままでは精度も利益も示せない」と指摘されたこと。繰り返し観察と確認が起きやすい日課だという仮定に基づく。排せつなど他場面への一般化は、食事場面で有効と分かってから検討する。この選定自体は仮説であり、食事が最頻の困りごとだという調査結果はない。
- 根拠: [意思決定支援ガイドライン](https://www.mhlw.go.jp/stf/newpage_76171.html)は言葉以外の反応の記録と仮説的な検討を重視する。声と意思に安定した対応があるかは未確認。特定のアプリの有効性を示した資料ではない。
- 意図: 担当者が変わっても、本人への確かめ方を引き継ぐ。意思そのものを機械が決めることではない。

## 3. What：解決策と最小の体験

- 候補: 食事場面の既存の具体例と、そのときの対応・本人の反応を検索し、職員が似た場面で確認する。
- 操作フロー案（食事場面）:
  1. 職員が今の観察を書く。事実と解釈は分けて書く。
  2. 関連する過去例と出典を見る（誰が、いつ、何を観察し、どう確認し、本人がどう反応したか）。
  3. 職員が確認方法を選んで本人に確かめる。
  4. 結果を次の4欄に記録する。この4欄は強みとして残す。
     - 事実（観察したこと）
     - 解釈（職員がそう取った理由。正解とは書かない）
     - 確認方法（本人へどう確かめたか）
     - 本人の反応
- 対象外: 声や身振りだけで本人の意思を確定する機能、全利用者に共通する分類器、ベテランの推測を教師データの正解にすること、食事以外の場面を最初から対象にすること。

## 4. How：Google技術と候補比較

- 実行基盤の候補: Cloud Run（[指定の6種類](../README.md#要件の扱い)のうちの仮説。未採用・未実装）。
- Gemini が必要だと仮定する具体条件（仮説）: 同じ人の食事記録が、職員によって違う言葉で書かれているとき。例として、「体をゆする」と「左右に動かす」、「残渣」と「口の中に食べ物が残っていた」のように、意味は近そうでも表記が違う記述を想定する。これらは説明用の仮の言い回しであり、実在の記録ではない。キーワードやタグ、場面名だけのルール参照では関連例を逃し、新人は似た確認の仕方にたどり着けない、という仮定。このとき Gemini（Vertex AI 経由を候補）は意思を判定せず、言い回しの違いを越えて出典付きの過去例を返す。
- 比較する流れ: 同じ食事の観察文に対し、ルール参照（キーワード・タグ・場面＝食事）と Gemini による関連例抽出を並べて見せ、職員が確認方法を選んだうえで4欄に記録する。

| 候補 | 役割・採用理由の仮説 | メリット | デメリット・要確認 |
| --- | --- | --- | --- |
| ルール参照（キーワード・タグ・場面＝食事） | 表記が揃っている記録を確実に出す | 結果が追える。誤った関連付けが起きにくい | 言い回しが違うと関連例を逃す（仮説） |
| Gemini（Vertex AI 経由を候補） | 言い回しの違いを越えて関連例を出し、出典を示す | 自由な記述から似た確認例を探せる（仮説） | 誤った関連付け、個人別データの不足、記録の偏り。意思の判定に使えば誤解を固定し得る |
| Cloud Run | 検索と画面の指定実行基盤候補 | 記録参照をサーバー側に寄せられる | アクセス制御・費用の設計。未実装 |
| 既存の記録ソフト、紙の引き継ぎ、ベテランへの相談 | 比較対象 | 現場で既に使われている | 担当が変わると確かめ方ごと引き継げない場合がある（仮説）。効果は未確認 |

- 採用技術: 未採用・未実装。Gemini を中核にするかは、次節の検証と棄却条件で決める。
- ルールによる参照で足りる可能性は、自ら認める。足りると分かった場合は、下の棄却条件に従い案を捨てる。

## 5. AIをどこで、なぜ使うか

- 利用を限定する場面: 食事場面の過去例を、言い回しの違いを越えて整理・参照する補助に限る。職員の解釈も、AIの関連付けも、本人の意思の正解とは決めない。
- そこで使う理由（仮説）: 観察の書き方が職員ごとにぶれると、ルール参照だけでは似た確認例に届かない、という仮定のため。この仮定が成り立たなければ Gemini は不要である。
- 人間が確認すること（強み）: 観察した事実、解釈、確認方法、本人の反応を分ける。提示された過去例の出典を開き、採用する確認方法を職員が選ぶ。
- 文書整理・調査でのAI利用は[共通記録](../intellectual-disability-welfare-review.md#ai利用と判断)を参照。

## 6. 検証・完成度・デモ

- 検証方法（仮説の確かめ方）:
  1. 同じ架空の食事記録（許可が取れた場合に限り、個人が特定できない範囲の実記録）に対し、ルール参照と Gemini の関連例抽出を並べ、出せた出典付きの有用例を比べる。
  2. 新人役の職員が、提示された例を見て確認方法を選べたか、4欄を書けたかを見る。
  3. 記録の入力が新たな負担になっていないかを、本人への確認の質が上がった実感と一緒に聞く。実測値は未取得のため書かない。
  4. 食事場面の職員から、個人情報を含めずに「今どう確認しているか」「担当変更で困ったか」を聞く。ヒアリングは未実施。
- デモで示せること: 架空の食事場面で、観察を入力して過去例と出典を見る → 確認方法を選ぶ → 4欄に記録する、という操作の流れ。
- デモで示せないこと: 実際の本人の意思を読み取れる精度、現場での利益。架空検索だけではこれらを示せない、という第1回の指摘は妥当であり、ここでもそう書く。
- ピッチで説明する結果: 新人職員が確認方法を選び、本人の反応を記録できたこと。正しい意思を当てたことではない。
- データの公開や常時録音を前提にしない。本人別のデータ、利用条件、確認方法が必要。

## 7. 未決定事項・次の確認・学び

### 選定しなかった理由（残している論点）

- 個別対応が必要なことと、データから意思を分類できることは別。
- ベテランの推測を教師データの正解にすると、誤解を固定するおそれがある。4欄で解釈と本人の反応を分けるのは、このリスクへの対抗策であり、解釈欄を正解扱いにした時点で案は成り立たない。
- 発声・行動は場面や関係性で変わり得る。本人への確認を省略する根拠はない。
- 記録入力と結果確認が新たな負担にならないか、未確認のままである。

### 棄却条件

次のいずれかを満たしたら、記載どおりに捨てる。

1. 同じ食事記録の集合で、ルール参照が Gemini と同じかそれ以上に、確認に使える過去例を出せる → Gemini を採用しない。その場合、本案は Google 技術を中核にした提出案としては捨てる。
2. 4欄の記録とルール参照だけで、新人が確認方法を選べる → Gemini を中核にした本案を捨てる。4欄そのものは強みとして、他の運用や別案に残してよい。
3. 4欄の入力が新たな負担になり、本人への確認の質が上がらない → 案を捨てるか、欄を減らして再設計する。負担だけ増えるなら提出しない。
4. 食事場面の職員ヒアリング（個人情報を含まない）で、今困っている確認が食事にない、または既存の申し送りで足りている → この場面設定を捨てる。代わりの1場面を取り直せない、またはどの場面でもルール参照で足りるなら、案自体を捨てる。

再検討条件: 食事場面での現在の確認方法と、共有可能な情報の範囲を把握できること。学びは、推定の自動化と意思確認の支援を区別する必要があること、および Gemini が要る条件を場面と表記ゆれに絞らないと検証できないこと。開発による学びは未記入。
