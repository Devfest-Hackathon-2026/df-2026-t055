# パーソナル観光提案アプリ

- 投稿: Koki🍙(ちよ)18:14
- 状態: 仮置き・未検証。以下の具体化は検討用の仮説。
- 記入方針: 元の案と追加の仮説を分ける。出典・効果・実績を推測で確定しない。
- レビュー反映: 2026-11-05、Kokiとの批判的検討（個人向け提案は既存のパーソナルAIエージェントで足りるという前提に立ち、案の存続条件と対象範囲を見直した）を受けて改訂。
- 弱点改善の改訂: 2026-11-05、競合調査で判明した弱点（しおり共有・投票・AIドラフトは既存が実装済み）を受け、「制約の合成と公平な配分」と「当日の再解決」に中核を移した。

## 1. 元の案

- 最初はパーソナライズされたパンフレットを作成するアプリを想定。

  →パンフレットの良さをデジタルにうまく融合したい

- museやgrokbotのようなパーソナルAIエージェントの登場により、実現がやりやすいように思える。

  →ただパーソナルAIエージェントを使うのと差別化をさせないといけない

- 個人だけでなく集団で旅行に行く時はコンテキストを共有して、全員に最適化させたい。
- また現在地と予定を照合して動的に、空き時間の提案や、注意事項などを喚起する。

## 2. Why：誰の、どんな課題か

- カテゴリ候補: 観光
- 対象ユーザー・困る場面（仮説）:
  - 幹事役: 友人グループの旅行で、全員の希望（行きたい場所・食べ物・予算・体力）を聞き取り、衝突を調整し、行程表を作る負担が1人に集中する。調整の過程が見えないため「なぜこの行程になったか」で揉める。
  - 参加者全員: 当日に雨・行列・早閉まいなどで予定が崩れるたび、現在地と残り時間から代替案をその場で調べ直す負担がかかる。
  - 団体旅行の幹事（対象候補として追加）: 修学旅行・社員旅行・合宿・サークル旅行など、アレルギーや身体面の制約が「好み」ではなく絶対条件になり、公平さへの説明責任も生じる場面。ここでは制約の扱いと公平性は任意の工夫ではなく必須要件になる。
- 解決したい社会課題（仮説）: 旅行情報が分散し、全員の希望や時間の制約を踏まえた合意形成と、当日の変更対応が難しいこと。個人の好みだけなら既存の手段でも足りる場面が多く、「集団」と「当日」の2点に課題を絞る。
- 批判的検討（2026-11-05、Kokiとの議論）:
  - 1人向けの観光提案・旅程作成は、muse・grokbot 等のパーソナルAIエージェントで十分に足りる領域であり、そこを主戦場にする新規サービスは成立しにくい。この前提を認め、対象から外す。
  - 一方でパーソナルエージェントは設計上「1人のため」のものであり、グループ全員の希望・NG・体力は誰か1人のエージェントからは見えない。集団の合意形成は「機能不足」ではなく「前提の違い」として残る差別化の余地がある（仮説）。
  - 旅行には臨時休業・悪天候による移動困難などイレギュラーが常にある。当日に状況へ応じて再提案し、予定変更をこちらから促す体験は、静的な旅程作成との差になる（ただし成否はデータの正確さに依存する。第6節参照）。
  - 案の存続条件: 「幹事の負担と希望調整の痛み」が実在し、既存エージェント＋人間の調整では不十分だと確認できなければ、この案自体が成立しない。ヒアリングで最初に潰す。
- 根拠: 未確認。グループ旅行経験者に「幹事の負担」「希望の衝突」「当日の予定変更」で困った場面を聞き、出典・日付を追記する。03の行き先マッチング案との課題の違い（決定前／決定後）もここで整理する。
- 人間が決める意図: パンフレット（しおり）の良さ＝「編集された1つの共有物を全員で眺めて決める体験」と定義し、全員の希望の扱い（全員最適が無理な場合の見せ方）をAI任せにせずチームで決める。

## 3. What：解決策と最小の体験

- 解決の仕組み（仮説）: 3つの要素で構成する。
  1. グループコンテキストの合成: メンバー全員が短いフォームで「行きたいこと・NG・予算・体力（歩ける量）」を登録し、グループ全体の条件として自動合成する。個人の希望は誰のものか分かる形で保持する。
  2. しおり形式の旅程: 合成した条件から旅程を「しおり」として生成し、共有リンクで全員が同じものを見る。各スポットに「誰の希望か」「なぜこの順番か」「注意点（閉店時間・所要時間）」を明示し、比較と合意をしやすくする。
  3. 当日モード: 現在地・次の予定・営業時間・天気を照合し、空き時間の使い方の再提案と、「そろそろ出ないと閉店／終電に間に合わない」といった注意喚起を行う。
- ポジションの明確化（弱点改善）: 計画づくり自体は既存サービス（tabiori、Wanderlog、各種AI）が強い領域なので、本案の主戦場は「事前の計画」ではなく「当日の再解決」に置く。しおりは既存ツールやチャットで決めた行程を取り込める形も検討し、当日に予定が崩れたとき、全員の制約を守ったまま解き直して先回りで提案する層に特化する。
- 希望が衝突したときの扱い（仮説）: 全員が満足する解がない場合は隠さず、「誰がどこで譲ったか」を見える化したうえで、代替案（その時間だけ別行動＋合流地点の提示）を出す。多数決で切り捨てないことを差別化の一部とする。
- 公平性の設計（弱点改善で中核に格上げ）: 投票型の合意形成（Troupe 等）と違い、本案は希望を「硬い制約」と「希望」に分けて扱う。
  - 硬い制約（アレルギー、身体的に歩けない距離、予算の上限など）は票数に関わらず絶対に破らない。候補の生成時点で除外する。
  - 希望が衝突した場合は「譲り合い」を数値として配分する。前のスポットや前日で譲った人の希望を次で優先するなど、旅行全体で不公平が偏らないようにし、その配分経過を全員に見せる。
  - これにより、声の大きい人や多数派に引っ張られる投票の弱点を避け、幹事が「なぜこの行程か」を説明できる根拠を作る。
- 操作フロー案: メンバーが各自フォーム入力 → グループコンテキストを合成 → しおりを生成・共有リンクで全員が確認 → 全員で候補を調整・確定 → 当日はモードを切り替え、空き時間や予定変更のたびに再提案を受ける。
- MVP候補:
  - 1地域・1グループに絞る
  - メンバーフォーム（好み・NG・予算・体力）とグループコンテキスト合成
  - しおり形式の旅程生成（共有リンク付きWebページ）
  - 当日モード（現在地と次予定は手動更新も可）での空き時間提案と出発・閉店の注意喚起
  - 営業時間・移動時間は Google Places／Routes 等の実データから取得し、AIに事実を作らせない
- 普及の壁への対策（仮説）: 新規サービスは「コンテキストを集め直す」負担が普及を妨げる。これに対して:
  - 集めるコンテキストは「この旅行についての希望・NG・予算・体力」に限定する。利用者の生活全体の情報は持たない（数分のフォームで完結させる）。
  - メンバーはアカウント登録なしで、共有リンクからフォーム入力としおり閲覧ができる形にする。幹事以外にインストールや登録を求めない。
  - カレンダーや現在地など重い情報は、連携に頼らず手入力・任意連携で代替可能にする。
- 今回の対象外候補: 1人向けの旅程作成（パーソナルAIエージェントで代替可能と判断）、予約・決済（提案と外部リンクまで）、全国対応、常時の位置追跡、全日程の自動確定、交通機関の遅延など外部要因の完全な予測。
- 既存の手段との差（2026-11-05 競合調査を実施。以下は確認できた事実と、それを踏まえた仮説）:
  - tabiori（タビオリ）: 旅のしおりの作成・共有の定番。共同編集、招待URL／QRでの参加、旅行期間中の位置共有、アプリ内チャットまで備える。「しおり＋リンクで全員が見る」だけでは差にならない。
  - Troupe: 行き先・日程をランキング投票で決める「合意形成」専門のサービス。投票による決定は既にカバーされている。
  - Wanderlog: 共有旅程の共同編集に、地図・地点間の移動時間・予算管理まで含む。
  - Trespot: グループの制約（日程、予算、優先順位など）からAIが日程ドラフトを生成する。「グループの条件→AI旅程」も既に存在する。
  - パーソナルAIエージェント（muse、grokbot等）との差: それらは「1人のための最適化」と「チャットで流れる回答」が前提。本案は「全員の条件の合成と衝突調整」と「残って全員で眺める共有物（しおり）」が中核で、構造的に担う対象が違う。
  - 残る差（仮説）: ①投票ではなく、硬い制約を絶対に破らず、譲り合いを公平に配分して見える化する調整（第3節の公平性の設計） ②既存が「作って共有する計画ツール」であるのに対し、当日に予定が崩れたらサービス側から再解決して提案する当日レイヤーへの特化。既存が機能追加で到達可能ではあるが、現時点の各サービスの主戦場（計画と共有）とは軸が違う。差として成立するかは、幹事経験者のヒアリングで「それなら使うか」を確認する。
  - 需要の頻度に関する正直な懸念と対策: グループ旅行は多くの人にとって年に数回程度で、低頻度のサービスは定着・課金の面で構造的に厳しい。これは完全には解けない弱点として残る。緩和策の候補: ①継続利用を前提にせず「旅行ごとに使い捨て」で成立する体験にする（共有リンク経由で次のグループに広がる形） ②制約と公平性が必須になる団体旅行（修学旅行・社員旅行・合宿）を対象に含め、頻度ではなく必要性で選ばれる場面を作る。
  - 03（旅行先マッチング）との差: 03は行き先を決める前のマッチング、本案は行き先決定後の旅程と当日運用。採用時は境界を明記する。

- 採用しなかった案と理由: 未決定。チャット中心UI（流れて比較できない）／全自動の行程確定（人間の合意を飛ばす）／パーソナルAIへの丸投げ（差別化が消える）を比較対象として記録する。
- 拡張路線との比較（2026-11-05 検討）: 新規サービスではなく、既存のパーソナルAIエージェントの拡張（プラグイン／MCP 等で「グループ旅行の共有コンテキスト置き場」を各人のエージェントが読み書きする形）も技術的には有望な方向である。ただし、①全員が対応エージェントの導入と権限許可をする必要があり、普及の壁が「新規登録」から「全員のセットアップ」に移るだけであること、②情報共有の同意設計が必要なこと、③配布がプラットフォーム依存になること、そして今回のハッカソンでは「Google技術／Gemini が中核」という要件から外れることから、今回は採らず、将来の拡張として記録する。

## 5. AIをどこで、なぜ使うか

- プロダクト内の利用案: ①複数人の希望の合成と衝突の言語化 ②しおりの各スポットへの「誰の希望か・理由・注意点」の説明生成 ③当日モードでの再提案（空き時間の使い方）。
- その場面で使う理由: 条件の組み合わせと衝突の調整は、固定ルールだけでは「なぜこの案か」を説明しにくい。逆に、営業時間・移動時間のような事実は検索・APIで足りるためAIに作らせない。この切り分け自体を検証材料にする。
- 人間が判断・確認すること: 最終的な行き先の決定、衝突時に誰の希望を優先するか、提案の根拠（参照した営業時間・移動時間）の確認。両立しない条件はAIに無理に両立させず、対立として提示させる。
- 開発支援の利用実績: 文書整理の共通記録は[README](README.md#この文書でのai利用)を参照。以降は場面・使い方・理由・人間の判断を追記。

## 6. 検証・完成度・デモ

- 課題と効果の検証: 希望が実際に異なる3〜4人のグループに使ってもらい、①各自の希望（特にNG）が旅程に反映されたか ②しおりを見て候補を選ぶまでの時間と揉め具合 ③当日モードの再提案を採用したくなるか、を確認する。幹事役には従来の作り方（検索＋表計算等）との負担比較を聞く。結果は未検証。
- UI・UXの確認: 全員がスマートフォンで同じしおりを開き、候補・理由・注意点を見渡せるか、条件変更後に再生成して比較できるかを確認する。
- 安全性・データの扱い: 位置情報と予定の共有範囲を明示し、旅行終了後に残す履歴を最小化する。営業時間・移動時間には出典と取得日を示す。再提案の生成が失敗しても、確定済みのしおり表示は保持する。
- 拡張性・保守性: 1地域に絞り、「観光情報の取得」「条件合成・生成」「しおり表示」を分離し、地域やデータソースの差し替えができる構成を検討する。
- デモ構成案（3分想定）: 冒頭で「1人分の旅程なら既存のAIエージェントで足りる」と前提を置き、グループの場面から始める。京都、友達4人で希望がバラバラ（例：Aは海鮮を食べたい／Bは海鮮NG／Cは予算を抑えたい／Dはあまり歩きたくない）→ フォーム入力からしおりが生成され、「誰がどこで譲ったか」の配分が全員に見える → 当日、雨で予定が崩れて90分の空きが発生 → 硬い制約（Bの海鮮NG、Dの歩行限界）を守ったまま再提案が向こうから届く → 締めに「投票でも個人向けAIでもできない、制約の合成と当日の再解決」の2場面を強調する。天候変化など再現が難しい要素はシナリオとして再現可能にしておく。
