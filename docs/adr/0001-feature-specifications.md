# ADR-0001：仕様を機能ごとの文書群で管理する

## 背景

旧 `docs/PRODUCT_SPEC.md` は、機能要件、共通契約、検証、運用を1ファイルにまとめていた。機能ごとの実装範囲・受入条件・未確認事項を参照し、並行作業で変更範囲を分けられる構造が必要になった。

## 比較した選択肢

| 選択肢 | 利点 | 負担・判断理由 |
| --- | --- | --- |
| 単一の仕様書を維持する | 1ファイルで全体を読める | 機能ごとの変更・状態・参照先を分けにくい |
| 機能仕様と共通契約へ分割し、索引で結ぶ | 担当機能から必要な契約と検証へ進める。メタデータから一覧を生成できる | リンク・索引・メタデータの整合性検査が必要になる |

この比較は、再編時の差分と文書運用をもとに今回整理したもの。当時の比較会議や独立レビューが実施されたとは主張しない。

## 決定

**機能仕様と共通契約への分割を採用する。** 文書の実体を `docs/` に集め、実装の正本は `authority: normative` の文書群とする。OKFを参考に、1概念1Markdown、YAMLフロントマター、パスによる概念ID、Markdownリンク、索引と変更履歴を用いる。

採用の根拠は、2026-11-10にマージされた[PR #173](https://github.com/Genk-AI/df-2026-t055/pull/173)。本ADRは既存の判断を記録するもので、新しい機能要件を追加しない。参照版 `okf@v0.2` の固定とコミット前検査の追加は、記録時点では[PR #177](https://github.com/Genk-AI/df-2026-t055/pull/177)でレビュー中。

## 影響

- 機能の受入条件・コード・テスト・証拠・未確認事項は各機能仕様へ置き、一覧はメタデータから取得する。
- 共通契約を複製せず、機能仕様から参照する。旧仕様の節番号は移行表から解決する。
- 文書の `status` はOKFの `draft`・`stable`・`deprecated` とする。機能の実装状態は `implementation`、検証範囲は `verification` 等で別に記録する。
- ADRは判断理由を残す `authority: reference` の文書とし、仕様の正本を上書きしない。
